# 角色规则改用 skill，按角色预载

- **日期**：2026-09
- **状态**：已落地（本仓这一半）
- **触发**：`GTO-Trainer` 那边量上下文时发现，**每个 subagent 都在加载全部 8 份角色规则**，
  而它只用得上其中一份。issue：`GinkgoLeafLab/GTO-Trainer#195`

## 要解决什么问题

`.claude/rules/<角色名>.md` 这个名字看着像「只给那个角色的」，**实际上它对每个 agent 都加载**。
官方原话（<https://code.claude.com/docs/en/memory>）：

> Rules without `paths` frontmatter are loaded at launch with the same priority as `.claude/CLAUDE.md`.

`GTO-Trainer` 上的实测（2026-09-22，派两个不同角色的 subagent 各自自省，结论一致）：

| | 主会话 | subagent |
|---|---|---|
| `CLAUDE.md` | ✓ | ✓ |
| **全部 8 份角色规则** | ✓ | **✓（含跟自己毫无关系的 7 份）** |
| 自己那份角色定义（本仓这 8 份） | ✗（只有 `description`） | ✓ 作为系统提示注入 |

换算成 token（该仓实测标定 2.41 字节/token）：

```
每个 subagent 里
  自己那一份角色规则        平均  8.0k tokens   ← 需要
  跟它无关的另外 7 份       平均 56.1k tokens   ← 不需要
```

**这笔开销按 agent 数付，不是按会话付。** 那次会话主会话 + 3 个 subagent = 4 份，
光 memory files 就 ≈337k tokens。

问题因此不是「某几份规则太长」，而是**一份 8.0k 的东西被发了 8 份**。

判据：把「每个 agent 开工前先把另外 7 个角色的项目事实通读一遍」讲给人听，他不会觉得这是在做正事。

## 调研

**出处只有官方文档，但每条都是原话。** 本仓这次不做本地实验（agent 注册表在会话启动时定型，
新建的 agent 文件本次会话不认——这一条 `GTO-Trainer` 的 `CLAUDE.md` 已经记着）。

| 机制 | 按什么裁 | 出处（原话） | 用不用 |
|---|---|---|---|
| **`skills:` frontmatter** | **按角色** | *"Use the `skills` field to inject skill content into a subagent's context at startup."*、*"The full content of each listed skill is injected into the subagent's context at startup."*（<https://code.claude.com/docs/en/sub-agents>） | **选它** |
| skill 本身的加载形状 | 描述常驻、正文按需 | *"In a regular session, skill descriptions are loaded into context so Claude knows what's available, but full skill content only loads when invoked."*、*"Unlike CLAUDE.md content, a skill's body loads only when it's used, so long reference material costs almost nothing until you need it."*（<https://code.claude.com/docs/en/skills>） | 配套 |
| `paths:` 加在角色规则上 | **按文件** | *"Path-scoped rules trigger when Claude reads files matching the pattern, not on every tool use."* | 否，见下 |
| `omitClaudeMd: true` | 全有或全无 | *"Set to `true` to launch this subagent without the user, project, and local CLAUDE.md files"* | 否，见下 |
| `claudeMdExcludes` | 按路径 glob、会话级 | *"use `claudeMdExcludes` to skip CLAUDE.md files from other teams"* | 否，裁不到角色 |

**三个必答问题**

1. **有没有现成的标准做法？** 有，而且官方就是这么建议的。memory 文档里那条 Note
   几乎是照着这个问题写的：
   > Rules load into context every session or when matching files are opened.
   > **For task-specific instructions that don't need to be in context all the time, use skills instead**,
   > which only load when you invoke them or when Claude determines they're relevant to your prompt.

   skills 文档也点了同一件事：
   > Create a skill … **when a section of CLAUDE.md has grown into a procedure rather than a fact.**

   所以不是我们发明一个机制，是我们一直在用错机制。

2. **别人踩过什么坑？** 官方点了两个，都直接影响这个设计：
   - **预载不了「不许模型调用」的 skill**：*"You can't preload skills that set `disable-model-invocation: true`, since preloading draws from the same set of skills Claude can invoke."*
     → 角色规则那几份 skill **不许设** `disable-model-invocation`
   - **缺失是静默的**：*"If a listed skill is missing or disabled … Claude Code skips it and logs a warning to the debug log."*
     → 这条既是好消息也是坏消息，见「代价」

3. **有没有更省的路？** 有两条，都比这条省事，但都不够：
   - `paths:` 今天就能用、零跨仓工作量，**但它按文件裁、不按角色裁**。有天然地盘的只有
     `ci-dev` / `frontend-dev` / `backend-dev`，合计 15.3k / 64.1k = **24%**；
     而最大的两份（`code-reviewer` 18.5k、`cost-manager` 17.8k）恰恰按角色分工、没有地盘
   - `omitClaudeMd: true` 能一刀切干净，**但它连项目根的 `CLAUDE.md` 一起丢**。
     消费仓的 `CLAUDE.md` 里装着「禁止在 main 上直接提交」这类硬规矩，
     让 subagent 在不知道它们的状态下干活，比省下来的上下文贵得多

## 备选方案

| 方案 | 怎么做 | 代价 | 否掉的理由 |
|---|---|---|---|
| **什么都不做** | 每个 agent 继续吃 8 份 | 每派一个 agent 多烧 ≈56k tokens | 问题是实测的，而且随角色数线性恶化 |
| `paths:` 加在角色规则上 | 各仓自己做，本仓不动 | — | 只覆盖 24%，漏掉最大的两份。**不排斥**，可以叠加 |
| `omitClaudeMd: true` | 本仓给部分角色加一行 | subagent 连 `CLAUDE.md` 都没有 | 丢掉的是硬规矩，不是噪音 |
| 把项目事实搬进本仓这 8 份 | 直接写进角色定义 | **破纯净约束** | 这是个公开仓，而且那些事实搬到别的项目就不成立 |
| **`skills:` 预载**（选定） | 见下 | 跨仓分两步 + 缺失是静默的 | — |

## 选定方案

**本仓这一半（这个 PR 做的就是它）：**

1. 8 份角色定义各加一行 frontmatter：
   ```yaml
   skills:
     - <角色名>-rules
   ```
2. 「开工前先做这件事」那一节的第 2 项改成**两态都成立**的写法：
   优先看预载进来的 `<角色名>-rules` skill；**没预载到就去读 `.claude/rules/<角色名>.md`**
3. 那一节后面加一句共用的话：**两处都没有就要自己说出来**（理由见「代价」）

**消费仓那一半（不在这个 PR 里）：**

把 `.claude/rules/<角色名>.md` 搬成 `.claude/skills/<角色名>-rules/SKILL.md`，
内容一个字不改、只加 skill 的 frontmatter。搬完之后那份就不再对全体 agent 常驻了。

**顺序必须是「消费仓先建 skill，再升本仓的 tag」**——反过来不会坏（缺失只是跳过），
但中间那段时间等于白发一个 tag。

### 明确不做什么

- **不在这个 PR 里动任何消费仓**。本仓改完打 tag，各仓自己决定什么时候重接、什么时候搬
- **不删除「没预载到就读 `.claude/rules/`」那条退路**。它不是过渡期的临时代码——
  一个仓可以永远不迁移，那也该正常工作
- **不给任何角色加 `omitClaudeMd`**
- **不在本仓建那 8 份 skill**。它们装的是项目事实，按纯净约束就不该在这儿
- 不碰 `paths:` 那条路。它和本方案正交，各仓想叠加就叠加

## 代价

- **一次性**：本仓 8 份文件各改两处；每个消费仓搬 8 个文件 + 重接一次 subtree
- **持续**：多了一层「skill 名和角色名要对上」的约定。名字写错 = 那份规则永远不预载
- **它挂了会怎样**——**这是本方案唯一严重的失效方式**：
  官方原话 *"If a listed skill is missing or disabled … Claude Code skips it and **logs a warning to the debug log**."*
  也就是说**一个消费仓把 skill 名字拼错，后果是那个角色从此拿不到项目事实，
  而唯一的提示在 debug log 里**——没有人会去看。

  所以这个 PR 里那句共用的话不是客套，它是**唯一的探测器**：
  > 两处都没有，就说出来。预载失败只写进 debug log，不会有任何东西提醒你——
  > 所以「我没拿到这个角色的项目事实」必须由你自己讲出来。

  **这是提示词级别的缓解，不是强制。** 要变成强制，得由各仓在自己的测试里断言
  「每份角色定义的 `skills` 名字，在 `.claude/skills/` 下都存在」——
  那条检查只能在消费仓写（本仓没有那些 skill，也不该有）。
- **钱**：不涉及

## 怎么算做完了

本仓这一半：

1. 8 份角色定义的 frontmatter 各有一行 `skills:`，名字是 `<name>-rules`，**和文件名对得上**
2. 8 份的「开工前」第 2 项都写成了两态写法，**退路那一半逐字还在**
3. 打出一个新 tag

整件事做完（跨仓，不在这个 PR 的验收范围里）：

4. 某个消费仓搬完 skill 之后，派一个 subagent 自省一次，确认
   **它只拿到自己那一份项目事实、拿不到另外 7 份**

## 落地之后

- 本仓没有常规文档（根目录就是那 8 份角色定义），所以**现状写在角色定义自己里**
  ——「开工前先做这件事」那一节就是它
- 消费仓那边的现状各自写进各自的 `CLAUDE.md` 与搭建文档
- **本文件从此不再更新**
